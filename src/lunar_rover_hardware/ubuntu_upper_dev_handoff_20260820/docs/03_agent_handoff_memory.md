### 3.2 舵轮

已完成：

- H7 通过 UART7 接四路板
- 舵轮角度模式 / 速度模式
- `$STD` 遥测
- 四路板 RAW 透传

排查和修复过的关键问题：

1. `UART7` 波特率最初错误，后来确认必须改成 `115200`
2. 最初舵轮“点一次只动一点”的原因，不是网页，而是下位机把位置模式也按 `200ms` 死手超时处理
3. 现已改成：
   - 速度模式超时 `200ms`
   - 位置模式超时 `2s`
4. 上电后自动零位也已补上
   - 每一路首次收到有效反馈后，自动把当前位置记为零位

一个重要架构结论：

- 网页层不应该负责持续重发同一个位置目标来“帮下位机到位”
- 正确结构必须是：上位机单发目标，H7 自己保持闭环到位

### 3.3 机械臂

已完成：

- H7 通过 UART10 与机械臂舵机控制板通信
- `$ARM:PING / READ / MOVE / STOP / TORQUE / MULTI / RAW` 命令桥接
- Web 页机械臂单关节和 IK 调试

排查和修复过的关键问题：

1. 机械臂最初无响应，后确认硬件接线存在 TX/RX 问题
2. 软件侧确认 `UART10 = 115200`
3. 为降低 USB 回读乱码，把机械臂读取应答合并成单条 `$ARM:RESP,...!`
4. Web 页 `IK 初始位` 原来只让机械臂回位，前端缓存姿态没归位，会导致下一次键盘控制突然发出很大动作
5. 该问题已修复，Home 后前端缓存和示意图会同步回到初始位

## 4. 用户明确给出的硬件约定

这些约定是后续上位机开发必须继承的：

- 3508 顺序：右后、左后、右前、左前 = `1,2,3,4`
- 舵电机顺序与 3508 一致
- 四个 3508 都在 `CAN1`
- 四路板接 `UART7`
- 机械臂控制板接 `UART10`

## 5. 联调中得到的通信结论

### 5.1 USB CDC 共享不是不能用，但要避免粗暴并发

USB CDC 上同时承载：

- 3508 遥测
- 舵轮遥测
- 机械臂命令应答

曾经出现过“网页 RX 乱码”问题。根因不是单一硬件错误，而是这些因素叠加：

- 机械臂回读字符串被拆成多次 `CDC_Transmit_HS`
- 多模块同时往 USB CDC 打印
- CDC 队列偏浅

后续做过的处理：

- 机械臂应答改成单次整帧发送
- CDC 发送队列深度从 `8` 提到 `32`

### 5.2 高频特性

实测和代码层面可以得出：

- `ARM PING` 到 `33 Hz` 基本稳定
- 机械臂 `READ` 不是越高越好，`5 Hz` 左右就开始更容易暴露控制板或链路问题
- 因此上位机若需要机械臂状态，不建议长期高频同步读位置

建议：

- 平时主要靠“命令已知目标态 + 必要时低频校验”
- 不要设计成每个控制周期都同步阻塞读机械臂位置

## 6. Web 工具在整个调试中的角色

Web 页的目标一直不是成为最终产品，而是：

- 替代手敲控制台命令
- 让用户现场快速点按钮验证机构
- 做轻量级回读可视化

所以上位机正式开发时，应该把它视为：

- 协议样例
- 交互草图
- 调试参考

而不是最终软件架构本身。

## 7. 对下一位 Ubuntu 上位机开发 Agent 的建议

### 7.1 先做什么

优先顺序建议：

1. 建一个统一串口层，只连接 H7 的 USB CDC
2. 把三类协议按前缀拆成三个 client
3. 先把“发命令 + 收反馈 + 日志记录”跑稳定
4. 再做 GUI、IK、任务编排

### 7.2 哪些结论不要再重复试错

- 舵轮四路板不是 `921600`，当前工程里已经实机确认要用 `115200`
- 位置模式不该靠网页持续补发
- 机械臂板波特率已经确认是 `115200`
- 共享一个 USB CDC 是可行的，但协议帧必须整帧发送、整帧解析

### 7.3 仍值得继续完善的地方

- 给舵轮增加更完整的多通道遥测格式，不要长期只看 `$STD` 的简化文本
- 给 H7 增加更清晰的系统状态帧，比如 USB TX busy、丢包计数、各模块频率
- 机械臂如果以后要做正式闭环状态同步，应该设计更稳妥的异步状态采集方案
